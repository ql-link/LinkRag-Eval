# Robust Fusion R2 source lock executor v7.1

Status: `POST_AUTHORSHIP_IMPLEMENTATION_ERRATUM_AWAITING_SEAL`

This document records a fail-closed execution defect found after all 128 v7 source proposals had received their first mechanical PASS, but before a formal source-data lock, encoder execution, or human review. The sealed v7 `lock-data` entry rejected same-family candidate pairs whose template signatures become identical after numeric/version placeholders are normalized. Its `validate_no_cross_r2_duplicates` implementation accumulated each field immediately, so it treated within-family comparisons as cross-R2 comparisons. This is incompatible with the frozen design: exact/template/5-gram exclusion is across families/cross-slot, while equivalent and factual-conflict candidates within one family are intentionally matched and may differ only in a frozen numeric, version, direction, or applicability slot. The inherited R2SRC-002 also demonstrates that the old final check cannot be satisfied without replacing an already hard-locked proposal.

V7.1 supplies the missing correctly scoped source-lock executor. It does not modify or supersede the v7 scientific protocol, parser, slot registry, accepted proposal ledger, proposal hashes, first-PASS locks, R1 exclusion registry, 128-family denominator, 44/42/42 quota, 12 cells, 4×4×2 mapping, edit bands, estimand, encoders, human scale, measurement thresholds, or Gate rules. The failed v7 lock invocation produced no `data_lock` directory and is retained in the process record.

The v7.1 final recheck applies exact normalized-text hash, template signature, and 5-gram Jaccard exclusion between different query families only. All four texts of a current family are compared with every text from previously accepted families; they are not compared with one another for template or 5-gram duplication. Four-way normalized text uniqueness inside each family remains mandatory and is re-established by the unchanged parser/base materializer. The first mechanically accepted object for every slot remains immutable; no proposal is rewritten or replaced.

The v7.1 implementation, runner, tests, this specification, the sealed v7 preparation receipt, and the four append-only v7 ledgers must be hashed into an independent preparation manifest before the executor may write source data. The executor must reverify those hashes, refuse replay or overwrite, materialize all 128 accepted rows, assign the frozen mixed generator provenance, enforce the fixed denominator and quota validation, and write the formal source data lock append-only. Encoder execution remains forbidden until that lock succeeds.
